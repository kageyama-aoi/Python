# 06 設計パターン（Handler と Factory）

## IT新人向け

### 設計パターンって何？

プログラムを作るときによく出てくる「問題」には、先人が考えた「解決策」があります。
それを **デザインパターン** と呼びます。

料理のレシピのように、「この状況ならこう書く」という定石です。
名前がついているので、チームで「Factoryパターンで作ろう」と話せば伝わります。

### このプロジェクトで使っているパターン

| パターン | どこで使っているか | 何を解決するか |
|---|---|---|
| **Handlerパターン** | `src/scraping/handlers/` | 「モードごとに処理が違う」問題 |
| **Factoryパターン** | `src/scraping/handler_factory.py` | 「どのHandlerを使うか選ぶ」問題 |
| **Templateパターン** | `BaseHandler` の継承 | 「共通の枠組みを強制する」問題 |

### 具体的な動き（図解）

```
ユーザーが「Task Report」を選んで [実行]
      ↓
HandlerFactory が作られる
      ↓
school_type が "cl" か確認
      ↓ No（TRモードなので）
TaskReportHandler を作って返す
      ↓
TaskReportHandler.execute() を実行
      ↓
ブラウザでTRを自動入力
```

## 中級者向け

### Handlerパターン：「同じ操作・違う実装」

ブラウザ操作には「ログインしてデータを取る」という共通の流れがあります。
しかし CrowdLog と TaskReport ではログイン先も操作手順も全く違います。

**共通の「型」を決める（抽象クラス）**

```python
# base_handler.py
from abc import ABC, abstractmethod

class BaseHandler(ABC):
    def __init__(self, driver, context: dict):
        self.driver = driver
        self.context = context

    @abstractmethod
    def execute(self):  # ← 必ず実装しなければならないメソッド
        pass
```

`@abstractmethod` デコレータをつけると、`execute()` を実装していないクラスは
インスタンス化（`CrowdLogHandler()` で生成）しようとするとエラーになります。
「実装を忘れた」というバグを防ぎます。

**具体的な実装（具象クラス）**

```python
# crowdlog_handler.py
class CrowdLogHandler(BaseHandler):
    def execute(self):
        # CrowdLog固有の処理

# task_report_handler.py
class TaskReportHandler(BaseHandler):
    def execute(self):
        # TaskReport固有の処理
```

`main.py` は `handler.execute()` を呼ぶだけで、
`handler` が CrowdLogHandler でも TaskReportHandler でも同じコードで動きます。

### Factoryパターン：「作り方を隠す」

```python
# handler_factory.py
class HandlerFactory:
    def __init__(self, driver, context):
        self.driver = driver
        self.context = context
        self.handler = self._create_handler()  # ← 生成ロジックを内部に隠す

    def _create_handler(self):
        school_type = self.context.get('schools_type')
        if school_type == 'cl':
            return CrowdLogHandler(self.driver, self.context)
        else:
            return TaskReportHandler(self.driver, self.context)

    def execute(self):
        self.handler.execute()
```

**main.py 側（Factory を使う側）**

```python
# main.py
factory = HandlerFactory(driver, context)
factory.execute()  # どのHandlerかを気にしなくていい
```

`main.py` は「どのクラスを使うか」を知りません。
Handler の種類が増えても `main.py` を変える必要がありません。

### 継承と委譲の使い分け

このプロジェクトでは **継承** を使っています：

```python
class TaskReportHandler(BaseHandler):  # BaseHandler を継承
    def execute(self):
        ...
```

別のアプローチとして **委譲** もあります：

```python
class TaskReportHandler:
    def __init__(self, base):
        self.base = base  # BaseHandler を持つ（委譲）
```

一般的に「is-a 関係」（TaskReportHandlerはHandlerの一種）なら継承、
「has-a 関係」（TaskReportHandlerはLoggerを持つ）なら委譲が適切です。

## 上級者向け

### 抽象クラス（ABC）の意味

```python
from abc import ABC, abstractmethod

class BaseHandler(ABC):
    @abstractmethod
    def execute(self):
        pass
```

**`ABC` を継承する意味：**

`ABC`（Abstract Base Class）を継承することで、
`@abstractmethod` が指定されたメソッドを実装していないクラスは
**インスタンス化時にエラー** になります。

```python
class BrokenHandler(BaseHandler):
    pass  # execute() を実装していない

handler = BrokenHandler(driver, context)
# → TypeError: Can't instantiate abstract class BrokenHandler
#   with abstract method execute
```

これはコンパイル時チェックに近い効果を Python で実現しています。

### このパターンの拡張性

新しいモード（例：別会社のTRシステム）を追加する場合：

**変更が必要なファイル：**
1. `src/scraping/handlers/new_handler.py`（新規作成）
2. `src/scraping/handler_factory.py`（if文追加）
3. `src/scraping/handlers/__init__.py`（export追加）
4. `config/main.yaml`（メニュー追加）
5. `config/modes/task_report/new.yaml`（設定追加）

**変更が不要なファイル：**
- `main.py`
- `gui.py`（パターン追加ボタンで自動対応）
- `BaseHandler`
- 既存の他のHandler

これを **開放閉鎖原則（Open/Closed Principle）** と呼びます。
「拡張には開いている（新機能を足せる）・修正には閉じている（既存コードを変えなくていい）」

### Factory の改善：設定ドリブン化

現在の Factory は `if-else` で Handler を選んでいます：

```python
def _create_handler(self):
    if school_type == 'cl':
        return CrowdLogHandler(...)
    else:
        return TaskReportHandler(...)
```

新モードを追加するたびに `handler_factory.py` を修正する必要があります。
より高度な実装として **設定ドリブン Factory** があります：

```python
HANDLER_MAP = {
    'cl': CrowdLogHandler,
    # 'tr' は default として扱う
}

def _create_handler(self):
    school_type = self.context.get('schools_type')
    handler_class = HANDLER_MAP.get(school_type, TaskReportHandler)
    return handler_class(self.driver, self.context)
```

`HANDLER_MAP` に追記するだけで新モードに対応できます。

さらに進めると、`main.yaml` に `handler_class: "CrowdLogHandler"` を書いて
`importlib` で動的ロードする方法もあります（プラグインアーキテクチャ）。
ただし現プロジェクトの規模ではオーバーエンジニアリングです。

### context dict の型安全化（発展）

現在の `context` は `dict` のため、実行時まで型エラーが検出できません：

```python
# handler_factory.py での context 構築
context = {
    'schools_type': school_type,
    'environment_name': env_name,
    ...
}

# handler 内での利用（タイポしてもエラーにならない）
self.context.get('schools_typo')  # None が返るだけ
```

`TypedDict` で解決できます：

```python
from typing import TypedDict

class HandlerContext(TypedDict):
    schools_type: str
    environment_name: str
    keyword: str

# 以降、型チェッカー（mypy, pyright）がタイポを検出してくれる
context: HandlerContext = {
    'schools_type': school_type,
    'environment_name': env_name,
    'keyword': keyword,
}
```

`mypy` や VS Code の Pylance を使うと、
`context['schools_typo']` が存在しないキーとして警告されます。
