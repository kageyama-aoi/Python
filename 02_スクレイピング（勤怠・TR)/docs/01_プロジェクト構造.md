# 01 プロジェクト構造と src/ レイアウト

## IT新人向け

### フォルダ構成って何？

大きなプログラムは、1つのファイルに全部書くと管理できなくなります。
「この機能はこのフォルダ」というルールを決めておくことで、
どこに何があるかが一目でわかるようになります。

### このプロジェクトのフォルダ

```
02_スクレイピング（勤怠・TR)/
├── src/                 ← プログラム本体（ここを読めば動きがわかる）
├── config/              ← 設定ファイル（値を変えるだけでプログラムの動きが変わる）
├── tests/               ← 自動テスト（プログラムが正しく動くか確認する）
├── docs/                ← 技術ドキュメント（今読んでいるここ）
└── .output/             ← 実行結果の保存先
```

### src/ の中身

```
src/
├── main.py              ← 「スタートボタン」。ここから全てが始まる
├── config/              ← 「設定を読む係」
├── gui/                 ← 「画面を作る係」
├── scraping/            ← 「ブラウザを操作する係」
└── utils/               ← 「便利な道具箱」
```

### よくある疑問

**Q: なぜ `main.py` だけでなくフォルダに分けるの？**

A: 1つのファイルに全部書くと1000行を超えてしまいます。
   「画面の係」「ブラウザ操作の係」に分けることで、
   どこを直せばいいかがすぐわかります。

**Q: `config/` フォルダは何？**

A: プログラムを変えずに「プロジェクト名」「コメント文」だけ変えたいときに使います。
   設定ファイル（YAML）を編集するだけで動きが変わります。

## 中級者向け

### レイヤー分離の考え方

このプロジェクトは **関心の分離（Separation of Concerns）** という原則に従って構成されています。

```
[GUI層]         src/gui/          ← ユーザーの入力を受け取る
      ↓
[ビジネス層]    src/scraping/     ← ブラウザ操作ロジック
      ↓
[設定層]        src/config/       ← 設定値の管理
      ↓
[インフラ層]    config/*.yaml     ← 実際の設定データ
```

各層は **隣の層とだけ話す** のが理想です。GUI がいきなり YAML を直接読んだりしません。

### import の流れ

```python
# main.py が全体の司令塔
from config import config          # 設定を読む
from gui import gui                # 画面を起動する
from scraping.handler_factory import HandlerFactory  # 実行係を選ぶ
```

`main.py` はどのモジュールが何をするかを知っていますが、
各モジュールは互いのことをなるべく知らない設計になっています。

### `__init__.py` の役割

各フォルダに `__init__.py` があることで、そのフォルダが **Pythonパッケージ** として認識されます。

```python
# src/scraping/handlers/__init__.py の内容例
from .crowdlog_handler import CrowdLogHandler
from .task_report_handler import TaskReportHandler
```

これにより、外部から `from scraping.handlers import CrowdLogHandler` とシンプルに書けます。
内部のファイル名が変わっても、呼び出し側のコードを修正する必要がありません。

### config/ フォルダの 2 層構造

```
config/
├── main.yaml              ← 全モード共通の設定・メニュー定義
└── modes/
    ├── crowdlog.yaml      ← CrowdLog専用
    └── task_report/
        ├── common.yaml    ← TR全体の共通定義（フィールド名など）
        └── shimamura.yaml ← Shimamura固有の値
```

`config.py` が起動時にこれらを **ディープマージ** して1つの辞書 `CONF` に統合します。
設定ファイルを分割しているのは、「共通部分」と「プロジェクト固有部分」を分けるためです。

## 上級者向け

### アーキテクチャ評価

#### 良い点

**1. 設定とロジックの完全分離**

`config/` 配下のYAMLを変えるだけで新プロジェクトを追加できます。
`add_pattern()` メソッドを通じてGUIからも追加可能で、コードレスです。

**2. モジュールの独立性**

各 Handler は `driver` と `context` だけを受け取る純粋なロジッククラスです。
GUI や設定管理に依存しておらず、テストが書きやすい構造です。

**3. 段階的なマージ戦略**

```python
# config.py の _deep_merge
# main.yaml → modes/common.yaml → modes/{key}.yaml の順でマージ
# 後から読んだファイルが優先されるオーバーライド方式
```

#### 改善余地

**1. 循環依存のリスク**

現状、`config_manager.py` が `config.py` を import し、
`config.py` の `load_config()` を呼び出す構造です。
規模が大きくなると循環依存が起きやすいため、
`ConfigReloader` などの薄い中間層を挟む余地があります。

**2. `context` dict の型安全性**

Handler に渡す `context` が `dict` のため、キー名のタイポが実行時エラーになります。
`TypedDict` や `dataclass` で型を明示すると堅牢になります。

```python
# 改善例
from typing import TypedDict

class ExecutionContext(TypedDict):
    schools_type: str
    environment_name: str
    keyword: str
```

**3. `main.py` の直接パス依存**

`config_manager.py` 内の `"config/main.yaml"` が相対パスのハードコードです。
`pathlib.Path(__file__).parent` を使って実行場所に依存しない絶対パスにすると、
テスト時の `monkeypatch.chdir()` が不要になります。
