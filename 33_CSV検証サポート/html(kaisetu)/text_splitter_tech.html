text_splitter/src 技術解説（教材）

対象: text_splitter/src/run.py（コアロジック＋CLI）、 analyze.py（事前解析）、presets.py（プリセット管理）、 gui.py（単体GUI）。全体のアーキテクチャは main_kaisetu.html を参照。 本資料は他のコードを書くときにも転用できる汎用的な技術パターンを、 実装箇所を示しながら1テーマ1セクションで解説する「技術ポイント集」です。

1. ストリーム処理でメモリを使い切らない（split_csv）


with open(input_path, ...) as infile:
    reader = csv.reader(infile, delimiter=delimiter)
    for row in reader:
        ...
        writer.writerow(row)
        if rows_in_file >= options.rows_per_file:
            _close_current_file()

ファイル全体を list() や read() で一括ロードせず、 csv.reader が1行ずつ読み進めるイテレータであることを利用して、 読む→書く→捨てる、を行単位で繰り返している。

「数GBのファイルでも数MBのメモリで処理できる」のは、 データ構造の工夫ではなく一度に持つデータ量を1行分に保つという設計判断の結果。 巨大データを扱うコードを書くときは、まず「今、メモリ上に何行分のデータがあるか」を意識する癖をつけると良い。 fixed_length_formatter/src/run.py も同じ発想をバイト単位（1MBチャンク）で実践している。

2. dataclassで「入力」と「結果」を型として分離する


@dataclass
class SplitOptions:
    rows_per_file: int
    encoding: str
    has_header: bool = True
    delimiter: Optional[str] = None

    @classmethod
    def from_config_file(cls, config_path: Path) -> "SplitOptions": ...
    def validate(self) -> None: ...

@dataclass
class SplitResult:
    status: str
    total_rows: int
    output_summaries: list
    ...

「これから実行するパラメータ」（SplitOptions）と 「実行し終わった結果」（SplitResult）を、別々の dataclass として定義している。

dict を使い回すと「このキーは今どちらの意味か」が読み手にもIDEにも分からなくなる。 型を分けるだけで、関数のシグネチャ（split_csv(input_path, options) -> SplitResult） が「何を渡すと何が返るか」の仕様書になる。 from_config_file()（生成方法）と validate()（正当性検証）を データクラス自身に持たせている点も、「データとその整合性ルールをセットで管理する」という一貫した考え方。

3. 「賢い自動判定＋常に上書き可能」の二段構え（_detect_delimiter）


def _detect_delimiter(path, encoding, ext) -> str:
    candidates = {",": 0, "\t": 0, ";": 0}
    for line in 先頭20行:
        for delim in candidates:
            candidates[delim] += line.count(delim)
    best = max(candidates, key=lambda d: candidates[d])
    if candidates[best] > 0:
        return best
    return "," if ext.lower() == ".csv" else "\t"

区切り文字が指定されていない（None）ときだけこの関数が呼ばれる。 先頭20行だけをサンプリングして出現回数を数え、それでも判定できなければ拡張子に頼る、 という2段階のフォールバックになっている。

自動判定機能を作るときの型: 「まず自動で便利にする」→「自動判定が外れても、 明示指定（options.delimiter）があれば必ずそちらを優先する」。 このコードでも delimiter = options.delimiter or _detect_delimiter(...) という1行で、ユーザーの明示指定が常に自動判定より優先されることが保証されている。 「賢い機能」は必ず「利用者が上書きできる余地」とセットで設計する。

4. 遅延ディレクトリ作成 — 空振りの痕跡を残さない


run_output_dir = output_dir / f"{base_name}_{started_at:%Y%m%d_%H%M%S}"
...
for row in reader:
    if outfile is None:
        file_index += 1
        run_output_dir.mkdir(parents=True, exist_ok=True)   # ← ここで初めて作る
        output_path = run_output_dir / f"...split_{file_index:03}{ext}"

出力用のサブディレクトリのパスは実行開始時点で決まっているが、 実際に mkdir() するのは最初の1行を書き込む直前まで遅延させている。

もし入力ファイルが0行だったり途中でエラーが起きたりした場合、パスだけ計算して即 mkdir していると「中身が空のフォルダ」がゴミとして残る。 「作る」という副作用は、それが本当に必要になった瞬間まで遅らせるという考え方は、 ファイル生成以外（DB接続、一時ファイル、ロック取得など）にも応用が効く。

5. 進捗通知をコールバックとして外部から注入する


ProgressCallback = Callable[[str], None]

def split_csv(input_path, options, *, progress: Optional[ProgressCallback] = None):
    ...
    if progress and total_rows % 10_000 == 0:
        progress(f"  処理中: {total_rows:,} 行 ...")

split_csv 自体は「進捗をどう表示するか」を一切知らない。 ただ progress という関数を呼ぶだけで、その関数の中身（print するか、 GUIのキューに積むか）は呼び出し側が決める。

CLI（__main__ ブロック）は progress=lambda msg: print(msg, flush=True)、 GUI（gui.py）は progress=self._log_queue.put を渡す想定で、 同じコアロジックをCLIでもGUIでも書き換えずに再利用できている。 「表示方法」のような呼び出し元ごとに変わる関心事は、関数の中に埋め込まずコールバックとして 外から渡す、という依存性注入の最小形。

6. try/except/finally で「エラー時も後始末は必ず行う」


try:
    ...本処理...
except Exception as exc:
    status = "ERROR"
    error_message = str(exc)
    raise                      # ← 揉み消さず再送出
finally:
    if outfile is not None:
        outfile.close()
    write_log(log_path, result)  # ← 成功・失敗どちらでも必ず実行
except ではステータスの記録だけ行い、raise で例外を握りつぶさずに 呼び出し元へ伝える。一方で「ログを書く」「開いたファイルを閉じる」という後始末は 成功・失敗に関わらず必ず行いたい処理なので finally に置く。 「異常を伝える」ことと「後始末をする」ことは別の関心事であり、 except と finally の役割分担として書き分けるのが定石。
except Exception: raise だけを見ると「何のためにexceptしているのか」と 思うかもしれないが、これは status/error_message という 「ログに残すための状態」を書き込むためだけの捕捉であり、エラー処理自体は 呼び出し元に委ねている。except節が短いからといって不要とは限らない。

analyze.py は import 文を見ても分かる通り tkinter を一切importしていない。 GUIから呼ばれることを前提にした処理でありながら、GUIそのものへの依存を持たない。

「GUIから使われるロジック」と「GUIそのもの」は別モジュールに分けると、 GUIを起動しなくてもロジック単体でテストできる（実際 tests/test_analyze.py がある）。この分離のおかげで、ランチャー側（33_CSV検証サポート/launcher_gui.py）も importlib でこのモジュールだけを動的ロードして再利用できている （_load_analyze_module()）。「UIに依存しない層」を作ることは、 テスト容易性だけでなく再利用性にも直結する。

8. 巨大ファイルの行数カウントを「文字列化せず」高速に行う


def _count_rows(path: Path) -> int:
    count = 0
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1024 * 1024), b""):
            count += chunk.count(b"\n")
    return count

テキストとしてデコードせず、バイナリのまま 1MBずつ読んで b"\n" の出現回数を数えるだけで行数を数えている。

iter(lambda: f.read(N), b"") は「N バイトずつ読み、空バイト列が返るまで繰り返す」 という定番のチャンク読み込みイディオム。文字コードのデコードという重い処理を省略し、 bytes.count()（C実装で高速）だけで済ませているため、 数百MB〜数GBのファイルでも実用的な速度で行数を数えられる。 「本当に必要な情報は何か」を突き詰めると処理を減らせる、という良い例。

9. エンコード判定は「候補を順に試して例外で振るい落とす」


def _detect_encoding_from_file(path: Path) -> str:
    raw = ...先頭4バイト...
    if raw.startswith(b"\xef\xbb\xbf"):
        return "utf-8-sig"
    if raw[:2] in (b"\xff\xfe", b"\xfe\xff"):
        return "utf-16"
    for enc in ("utf-8", "shift_jis", "cp932"):
        try:
            with open(path, "r", encoding=enc, errors="strict") as f:
                f.read(65536)
            return enc
        except (UnicodeDecodeError, LookupError):
            continue
    return "不明"
BOM（バイト順マーク）という確実な手がかりを最優先で見て、 それがなければ候補エンコードを順番に「厳格モード（errors="strict"）で 実際に読んでみて例外が出るか」で判定している。 正規表現や統計的推定に頼らず、「本当にそのエンコードとして最後まで読めるか」を 実地で試すのが最も確実、という割り切り。候補の並び順（utf-8 → shift_jis → cp932）にも、 日本語Windows環境で遭遇しやすい順という実務的な意図がある。
read(65536) と読む量を制限しているのは全文を読まないための配慮だが、 裏を返すと先頭65536バイトより後ろに不正なバイト列があっても検出できない。 「サンプリングによる判定は万能ではない」ことは、この種の高速化手法とセットで意識しておく必要がある。

presets.py は「JSON形式のバリデーション」と「dictからSplitOptionsへの変換」しか 行っていない。分割ロジックには一切踏み込まず、最終的に run.py の SplitOptions という同じ型を返すことで、config.jsonから読んだ場合と プリセットから読んだ場合の後続処理を完全に同一にしている。 「新しい入力経路を増やす」ときは、既存の型に変換するアダプタを1つ足すだけでよい、という 型駆動の拡張しやすさの例。
KeyError のメッセージに「登録済みのプリセット一覧」を含めている点も 地味だが重要。エラーメッセージは「何が悪かったか」だけでなく 「次に何をすればよいか」まで含めると、利用者（未来の自分を含む）の手間を大きく減らせる。

11. GUIはロジックを持たず、3つのモジュールを「呼ぶだけ」にする（gui.py）


from analyze import _count_rows, _detect_encoding_from_file, _fmt_size, ...
from presets import load_presets, save_presets
from run import SplitOptions, _detect_delimiter, split_csv
gui.py のimport文を見るだけで、このファイルが「分割・解析・プリセットの ロジックを持たず、既存モジュールを組み合わせて画面を作るだけ」という設計方針が読み取れる。 importの並びは設計意図を最も雄弁に語る場所であり、依存関係を追うときは まずここを見るとファイル全体の見通しが立つ。
ただし launcher_gui.py は text_splitter パネルの実行を サブプロセス（python src/run.py <input>）として呼び出しており、 gui.py のように直接importして呼ぶ方式とは経路が異なる。 同じロジックでも「同一プロセス内でimportして呼ぶ」か「別プロセスとしてsubprocessで呼ぶ」かは 別の設計判断であり、この2つを混同すると「なぜこっちの改修がランチャーに反映されないのか」で ハマる（CLIの引数仕様を変えたら両方の呼び出し側を確認する必要がある、と text_splitter/CLAUDE.md にも明記されている）。

まとめ — ここで学べる技術パターンの一覧

パターン効果
ストリーム処理（1行/1チャンクずつ）メモリ使用量を入力サイズに依存させない
入力/結果を別dataclassに分離関数シグネチャが仕様書になる
自動判定＋明示指定で常に上書き可能賢さと制御可能性の両立
副作用（mkdir等）の遅延実行失敗時にゴミを残さない
進捗通知をコールバックとして注入同じロジックをCLI/GUI両方で使い回せる
except+raise / finally の役割分担異常伝播と後始末を独立に保証する
UI非依存のロジック層を切り出すテストしやすく、他所からも再利用しやすい
実地に読んでみて判定する（エンコード検出）統計的推定より確実な判定
薄いアダプタで入力経路を増やすコアロジックを変えずに拡張できる
エラーメッセージに次の一手を含める利用者の調査コストを減らす
どれも「text_splitterだから使える」特殊な技ではなく、 データ処理系のツールを書くときに繰り返し使える基本形。 次に自分でCLI/GUI両対応のツールを書くときは、まず「コア処理」「解析」「設定管理」「UI」の 4層に分けられないかを検討する所から始めると、このコードと同じ土俵に立てる。
