Lab 1. ファイルを「1行ずつ」読むとはどういうことか

これは何？
Python でファイルを読むとき、for line in ファイル: と書くと、 ファイルの中身を全部一気に読み込むのではなく、1行ずつ順番に渡してくれます。 この「必要な分だけ少しずつ扱う」やり方を、この資料では「ストリーム処理」と呼びます （水道の蛇口から少しずつ水が出てくるイメージです）。

手を動かす


# lab1.py

# 練習用の大きめファイルを作る（30万行）
with open("sample.txt", "w", encoding="utf-8") as f:
    for i in range(300_000):
        f.write(f"data-{i}\n")

# 1行ずつ処理する
count = 0
with open("sample.txt", "r", encoding="utf-8") as f:
    for line in f:              # ← ここが「1行ずつ渡してもらう」書き方
        count += 1
        if count <= 3:
            print(f"{count}行目: {line.strip()}")

print(f"合計 {count} 行を読みました")

実行結果イメージ：

1行目: data-0 2行目: data-1 3行目: data-2 合計 300000 行を読みました
なぜ大事？
もしこれが「ファイルの中身を一気に全部メモリ（作業机の広さ）に載せる」やり方だと、 ファイルが数GBもあるとパソコンが重くなったり止まったりします。 1行ずつ扱えば、机の上にはいつも1行分しか載らないので、ファイルがどれだけ大きくても平気です。

発展：試してみよう

  • range(300_000) を range(3_000_000) に増やしても、同じくらいの速さで動くか確認してみましょう
  • for line in f: の代わりに lines = f.readlines() （＝一気に全部読み込む書き方）に変えて、行数を増やしたときの違いを感じてみましょう
本物のコードではここ: text_splitter/src/run.py の split_csv() 関数内、 for row in reader:（163〜192行あたり）。CSVを読むときも同じ考え方が使われています。 上級編は「技術ポイント1」に対応。

Lab 2. 「設定」と「結果」を別の入れ物にする（dataclass）

これは何？
dataclass（データクラス）は、複数の値をひとまとめにして名前を付けて扱うための仕組みです。 辞書（{"rows_per_file": 1000, ...}）でも似たことはできますが、 dataclass を使うと「何という名前の値が入っているか」がコードを読むだけで分かります。

手を動かす


# lab2.py
from dataclasses import dataclass
from typing import Optional

@dataclass
class MyOptions:
    rows_per_file: int
    encoding: str
    has_header: bool = True
    delimiter: Optional[str] = None

    def validate(self):
        if self.rows_per_file <= 0:
            raise ValueError("rows_per_file は1以上にしてください")

opt = MyOptions(rows_per_file=1000, encoding="utf-8")
print(opt)
print("行数:", opt.rows_per_file)

opt2 = MyOptions(rows_per_file=-5, encoding="utf-8")
opt2.validate()   # ← ここで止まるはず

実行結果イメージ：

MyOptions(rows_per_file=1000, encoding='utf-8', has_header=True, delimiter=None) 行数: 1000 Traceback (most recent call last): ... ValueError: rows_per_file は1以上にしてください
なぜ大事？
「まちがった値が入っていないか確認する」処理（validate）を、 値そのもの（MyOptions）にくっつけておくと、値を使う人は毎回チェック方法を 調べなくても .validate() を呼ぶだけで済みます。 「データ」と「そのデータが正しいかを確認するルール」をセットで持たせる、という考え方です。

発展：試してみよう

  • validate() に encoding が空文字でないかのチェックも追加してみましょう
  • ValueError を try / except で受け止めて、 「エラーが起きました:」に続けてメッセージを表示するように書き換えてみましょう
本物のコードではここ: text_splitter/src/run.py の SplitOptions クラス（20〜44行あたり）。実際にはさらに from_config_file() という「設定ファイルから作る」機能も付いています。 上級編は「技術ポイント2」に対応。

Lab 3. コンピュータに「区切り文字」を当てさせる

これは何？
CSVファイルはカンマ区切りが多いですが、タブ区切りやセミコロン区切りのこともあります。 「先頭の数行を見て、一番たくさん出てきた記号をその区切り文字とみなす」という 単純な多数決で、区切り文字を自動的に当てることができます。

手を動かす


# lab3.py
def guess_delimiter(sample_lines):
    candidates = {",": 0, "\t": 0, ";": 0}
    for line in sample_lines:
        for d in candidates:
            candidates[d] += line.count(d)
    best = max(candidates, key=lambda d: candidates[d])
    return best if candidates[best] > 0 else ","   # 誰も勝たなければカンマを既定にする

lines_comma = ["a,b,c", "1,2,3"]
lines_tab = ["a\tb\tc", "1\t2\t3"]

print("カンマ区切りの判定結果:", repr(guess_delimiter(lines_comma)))
print("タブ区切りの判定結果:", repr(guess_delimiter(lines_tab)))

実行結果イメージ：

カンマ区切りの判定結果: ',' タブ区切りの判定結果: '\t'
なぜ大事？
自動で当ててくれると便利ですが、外れることもあります。だから実際のコードでは 「利用者が区切り文字を指定していたら、自動判定より必ずそちらを優先する」というルールも セットになっています。「便利な自動機能」には必ず「人間が上書きできる余地」を残す、という 考え方は覚えておくと役に立ちます。

発展：試してみよう

  • lines_semicolon = ["a;b;c", "1;2;3"] を作って判定させてみましょう
  • カンマとタブが両方ちょっとずつ混ざった行を作って、どちらが勝つか確かめてみましょう
本物のコードではここ: text_splitter/src/run.py の _detect_delimiter() 関数（66〜80行あたり）。実際には先頭20行をサンプリングし、 誰も勝たなければ拡張子（.csvならカンマ）で決めます。 上級編は「技術ポイント3」に対応。

Lab 4. フォルダは「本当に必要になった瞬間」に作る

これは何？
「これから使うかもしれないフォルダ」を先に作っておくと、結局何も書き込まなかったときに 空っぽのフォルダがゴミとして残ってしまうことがあります。 それを防ぐために、「最初のファイルを書き込む、まさにその直前」までフォルダ作成を遅らせます。

手を動かす


# lab4.py
from pathlib import Path

output_dir = Path("output_lab")

def process(rows):
    made_dir = False
    for i, row in enumerate(rows):
        if not made_dir:
            output_dir.mkdir(exist_ok=True)
            made_dir = True
            print("ここで初めてフォルダを作った！")
        print(f"{i}行目を書き込むふり: {row}")

print("--- 空のデータで実行 ---")
process([])
print("output_lab フォルダはある？:", output_dir.exists())

print("--- 中身ありで実行 ---")
process(["a", "b"])
print("output_lab フォルダはある？:", output_dir.exists())

実行結果イメージ：

--- 空のデータで実行 --- output_lab フォルダはある？: False --- 中身ありで実行 --- ここで初めてフォルダを作った！ 0行目を書き込むふり: a 1行目を書き込むふり: b output_lab フォルダはある？: True
なぜ大事？
「フォルダを作る」「ファイルを開く」のような、パソコンの中身を実際に変える処理を 副作用と呼びます。副作用は「本当に必要になるまで起こさない」ようにすると、 処理が空振りに終わったときにゴミが残らず、後片付けの手間も減ります。

発展：試してみよう

  • if not made_dir: の判定を外して、ループの前で毎回 mkdir するように書き換え、空データのときに何が変わるか比べてみましょう
本物のコードではここ: text_splitter/src/run.py の split_csv() 内、 run_output_dir.mkdir(parents=True, exist_ok=True)（173行あたり）が ループの中、最初のファイルを開く直前に置かれています。 上級編は「技術ポイント4」に対応。

Lab 5. 「進捗の表示方法」を後から差し替えられるようにする

これは何？
コールバックとは、「あとで呼び出してもらうために渡しておく関数」のことです。 処理の途中経過を「画面に表示する」のか「記録だけしておく」のかを、 呼び出す側（使う人）が自由に選べるようにできます。

手を動かす


# lab5.py
def count_to(n, on_progress=None):
    for i in range(1, n + 1):
        if on_progress and i % 3 == 0:
            on_progress(i)
    return n

print("--- 画面に表示するパターン ---")
count_to(10, on_progress=lambda i: print(f"{i}まで進んだよ"))

print("--- 記録だけするパターン ---")
log = []
count_to(10, on_progress=log.append)
print("記録された進捗:", log)

実行結果イメージ：

--- 画面に表示するパターン --- 3まで進んだよ 6まで進んだよ 9まで進んだよ --- 記録だけするパターン --- 記録された進捗: [3, 6, 9]
なぜ大事？
count_to という関数自体は「進捗をどう見せるか」を一切知りません。 だから同じ count_to を、コマンド画面用にもGUI画面用にも書き換えなしで使い回せます。 「表示の仕方」のような呼び出す人ごとに変わる部分は、関数の中に書き込まず外から渡す、 という発想です。

発展：試してみよう

  • on_progress に、進捗をファイルに書き込む関数を渡してみましょう （open("progress.log", "a") で追記モードにするヒント）
本物のコードではここ: text_splitter/src/run.py の split_csv() の progress 引数（10,000行ごとに呼ばれる）。 CLI（コマンド実行）では print を渡し、GUIでは画面更新用のキューに積む関数を渡します。 上級編は「技術ポイント5」に対応。

Lab 6. エラーが起きても「後片付け」だけは必ずやる

これは何？
Pythonで異常事態（エラー）が起きることを例外と呼びます。 try はまず試したい処理、except はエラーが起きたときの処理、 finally はエラーが起きても起きなくても必ず実行される処理です。

手を動かす


# lab6.py
def risky_divide(a, b):
    log = []
    try:
        result = a / b
        log.append(f"成功: {a} / {b} = {result}")
        return result
    except ZeroDivisionError as e:
        log.append(f"エラー発生: {e}")
        raise   # ← ここで「エラーがありました」と呼び出し元に伝える
    finally:
        print("ログ:", log)
        print("(成功でも失敗でも必ずここが実行される)")

risky_divide(10, 2)
print("---")
try:
    risky_divide(10, 0)
except ZeroDivisionError:
    print("呼び出し元でエラーを受け取った")

実行結果イメージ：

ログ: ['成功: 10 / 2 = 5.0'] (成功でも失敗でも必ずここが実行される) --- ログ: ['エラー発生: division by zero'] (成功でも失敗でも必ずここが実行される) 呼び出し元でエラーを受け取った
なぜ大事？
「ログを書く」「開いたファイルを閉じる」のような後片付けは、エラーが起きたかどうかに 関係なく必ずやりたい処理です。finally に置いておけば、 どんな終わり方をしても後片付け漏れが起きません。

発展：試してみよう

  • raise の行を消して実行し、except ZeroDivisionError: が 呼び出し元で反応しなくなる（エラーが「握りつぶされる」）ことを確認してみましょう。 これは実務でもやってしまいがちな失敗パターンです
本物のコードではここ: text_splitter/src/run.py の split_csv() 全体 （162〜219行あたり）。ログをファイルに書き出す write_log() の呼び出しが finally の中にあります。 上級編は「技術ポイント6」に対応。

Lab 7. 大きいファイルの行数を高速に数える

これは何？
ファイルの行数を数えるだけなら、中身を文字として読む必要はありません。 改行記号（\n）が何回出てきたかを、バイトのまま数えるだけで十分です。

手を動かす（Lab1で作った sample.txt を使います）


# lab7.py
import time

def count_naive(path):
    with open(path, "r", encoding="utf-8") as f:
        return len(f.readlines())

def count_fast(path):
    count = 0
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1024 * 1024), b""):
            count += chunk.count(b"\n")
    return count

start = time.time()
print("素朴な方法:", count_naive("sample.txt"), "行 /", round(time.time() - start, 3), "秒")

start = time.time()
print("高速な方法:", count_fast("sample.txt"), "行 /", round(time.time() - start, 3), "秒")

実行結果イメージ（ファイルサイズによって秒数は変わります）：

素朴な方法: 300000 行 / 0.045 秒 高速な方法: 300000 行 / 0.021 秒
なぜ大事？
「本当に必要な情報は何か」を考えると、無駄な処理を削れることがあります。 ここでは「文字として正しく読む」処理を省き、「バイト列の中の改行の数を数える」 だけにすることで速くなっています。ファイルが数百MB〜数GBになるほど差が大きくなります。

発展：試してみよう

本物のコードではここ: text_splitter/src/analyze.py の _count_rows() 関数（26〜31行あたり）。 上級編は「技術ポイント8」に対応。

Lab 8. 文字コードを「実際に読めるか試して」当てる

これは何？
日本語のファイルは utf-8 や shift_jis など、複数の文字コード （文字をバイト列に変換するルール）で保存されることがあります。 正しい文字コードで読まないと文字化けします。「候補のルールを順番に試して、 最後まで問題なく読めたものを採用する」というやり方で判定できます。

手を動かす


# lab8.py
def guess_encoding(raw_bytes):
    for enc in ("utf-8", "shift_jis", "cp932"):
        try:
            raw_bytes.decode(enc)
            return enc
        except UnicodeDecodeError:
            continue
    return "不明"

utf8_bytes = "こんにちは".encode("utf-8")
sjis_bytes = "こんにちは".encode("shift_jis")

print("UTF-8で作ったバイト列 →", guess_encoding(utf8_bytes))
print("Shift-JISで作ったバイト列 →", guess_encoding(sjis_bytes))

実行結果イメージ：

UTF-8で作ったバイト列 → utf-8 Shift-JISで作ったバイト列 → shift_jis
注意点
この方法は万能ではありません。バイト列によっては「本当は違う文字コードなのに、 たまたまエラーが出ずに読めてしまい、実は文字化けした結果を採用してしまう」ことがあります。 「エラーが出なかった＝100%正しい」ではなく「それらしく読めた」程度に考えておきましょう。 実際のコードは、さらに確実な手がかり（BOMという目印）も先にチェックしています。

発展：試してみよう

  • guess_encoding の候補リストから "shift_jis" を外して実行し、 Shift-JISのバイト列がどう判定されるか（文字化けが起きるか）確認してみましょう
本物のコードではここ: text_splitter/src/analyze.py の _detect_encoding_from_file() 関数（9〜23行あたり）。 上級編は「技術ポイント9」に対応。
