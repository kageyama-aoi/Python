33_CSV検証サポートを理解するための読み方ガイド

はじめに

本資料は、launcher_gui.py / text_splitter / fixed_length_formatter / diff_csv を中心としたコード群を、「どこから・どう読めば理解できるか」に特化してまとめたものです。 アーキテクチャそのものの解説は main_kaisetu.html を参照してください。

このフォルダは「1つの巨大なアプリ」ではなく、 3つの独立したCLIツール＋それらをまとめるランチャーという構成です。 どのファイルがどのツールに属するかを意識しないまま読み始めると、すぐ迷子になります。

1. やってはいけない読み方

  • launcher_gui.py を1行目から順に読む（1500行超あり、UI詳細に埋もれる）
  • 3ツールを同時に並行して読む
  • Tkinterのwidgetオプションを1つ1つ理解しようとする
launcher_gui.py は「サブウィンドウ4種＋パネル3種＋メインウィンドウ」という 多数のクラスが1ファイルに並んでいます。先頭から読むと、まだ出てこない ToolPanelBase の存在を知らずに個別サブウィンドウの詳細を追うことになり、 全体像を掴む前に消耗します。

2. このコード群の正体（最重要）

launcher_gui.py は「3ツールのGUIを実装したアプリ」ではありません。

各ツールの src/run.py をサブプロセスとして呼び出し、 標準出力をログとして表示するだけの「監督役」です。
  • 分割・変換・比較の実処理はランチャーの外（各ツールの run.py）にある
  • ランチャーが知っているのは「コマンドの組み立て方」と「出力フォルダの場所」だけ
  • ロジックを読みたいなら run.py へ、UIの挙動を読みたいなら launcher_gui.py へ、と目的で読む場所を分ける

3. 正しい読み順（全体像）

Step1  README.md で世界観を掴む（launcher_gui.py用 / 各ツール用）
Step2  ToolPanelBase（launcher_gui.py）を仕様書として読む
Step3  1つのツールに絞り、config用データクラス（Options）を読む
Step4  そのツールの run.py 本体処理を流れで読む
Step5  launcher_gui.py の実行フロー（サブプロセス起動〜ログ〜サマリー）を読む
「ランチャー全体 → 1ツールのオプション → 1ツールの本体 → ランチャーの実行制御」 という外側→中側→外側の順で読むのが最短です。

4. Step1：世界観を掴む

まず読むのはコードではなく README.md です。

  • 33_CSV検証サポート/README.md — ランチャーの画面構成・実行の流れ・ログ色分けルール
  • text_splitter/CLAUDE.md — アーキテクチャと注意点（ランチャーとのCLIインターフェース契約）
  • fixed_length_formatter/README.md / diff_csv/README.md — 各ツール固有の仕様
このプロジェクトはREADME/CLAUDE.mdが「設計判断の理由」まで書かれているため、 コードより先にREADMEを読む方が圧倒的に速いです。

5. Step2：ToolPanelBase を仕様書として読む理由

TextSplitterPanel / FixedLengthFormatterPanel / DiffCsvPanel はすべて ToolPanelBase の契約に従っています。

  • build_command() — 実行するコマンドラインを返す（唯一の必須メソッド）
  • run_input_label() / on_run_finished() / refresh() — 任意のフック
この4メソッドの役割を先に知っておくと、3つのパネルクラスの実装は 「このメソッドで何をしているか」という差分だけを追えばよくなります。

6. Step3：Options データクラスは仕様書

各ツールの run.py にある SplitOptions / FormatOptions は ロジックではありません。

そのツールが受け付けるパラメータの一覧表であり、 config.json のキーと1対1で対応しています。

本体処理（if 文や分岐）を読む前に、 「何が入力として渡ってきうるか」を from_config_file() と validate() から先に把握しておくと、本体処理の意図が読みやすくなります。

7. Step4：run.py 本体は「ストリーム処理」として読む

3ツールの本体処理はどれも共通の型を持っています。 

ファイルを開く
 ↓
先頭から少しずつ読む（全部をメモリに載せない）
 ↓
読んだ分だけ処理して都度書き出す・集計する
 ↓
finally で必ずログを書き出す
split_csv（行単位）、format_fixed_length（バイト単位）、 postcode_diff.load_postcodes（集合演算）と手段は違いますが、 「巨大ファイルでもメモリに全展開しない」という制約が3つとも共通の設計軸です。 知らずに読むと、なぜチャンク処理や set を使っているのか分かりません。

8. Step5：launcher_gui.py の実行フローは「キュー越しの1本道」

ここでようやく launcher_gui.py の中核（_on_run 〜 _on_run_finished）を読みます。 

_on_run（メインスレッド）
 → threading.Thread で _run_process を起動
    → サブプロセスのstdoutを1行ずつ log_queue に put するだけ
 → _drain_log_queue（100msごとのafterループ、メインスレッド）が
    log_queue から取り出して画面に反映
「ワーカースレッドは log_queue に put するだけで、 tkinterウィジェットには一切触らない」というルールさえ押さえれば、 サブウィンドウ4種の実装詳細を追わなくても実行フロー全体が理解できます。

9. ムズカシイと感じる正体

このコードが難しく感じるとしたら、能力の問題ではありません。

  • 1ファイルに複数の独立したクラス（サブウィンドウ×4、パネル×3）が並んでいる
  • 「今読んでいるのはランチャー側か、ツール本体側か」を意識しないと迷子になる
  • スレッド跨ぎの非同期処理（queue経由）が随所にある

規模は小さく見えて、「複数プロセス・複数スレッドを1画面にまとめる」という 実質フレームワーク的な設計です。

10. 実践的な読み方（おすすめ）

  1. まず1つのツール（例: fixed_length_formatter、最も小さい）の README.md を読む
  2. そのツールの run.py だけを、CLIのentry point（if __name__ == "__main__"）から遡って読む
  3. launcher_gui.py の該当パネルクラス（例: FixedLengthFormatterPanel）だけを読む
  4. build_command() が組み立てるコマンドと、run.py の argparse がどう対応しているかを照合する
「1ツールを縦に貫通して読む」のが最短です。 3ツールを横断的に理解しようとするより、1本理解できれば残り2本は同じパターンの繰り返しだと分かります。

11. まとめ

  • launcher_gui.py は「監督役」であり、ロジック本体ではない
  • 3ツールはそれぞれ独立したCLIとして完結している（ランチャーはその上に乗るだけ）
  • read順は「README → ToolPanelBase → Options → run.py本体 → 実行フロー」
  • 迷ったら「これはランチャー側の話か、ツール本体側の話か」を自問する
「分からない」のではなく「まだ正しい入口に立っていないだけ」です。 まずは1ツールを縦に読み切ることから始めてください。
